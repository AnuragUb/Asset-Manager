### What it is
Asset Manager / CineEAM — internal web app for CINEOM to track physical assets
(cameras, kits, IT gear): inventory, project assignment, returns/inspection,
QR tagging, employees, warranty, delivery challans, CRM/service integrations.

Active product is the web app. PowerShell/Electron are deprecated leftovers.

### Architecture (today)
SPA + Express API, single process serving both:
- Frontend: Vanilla JS ES modules (cache-busted query params like ?v=7.00)
- Backend: Monolithic server.js (~456KB) + utils.js + services/
- DB: PostgreSQL via Knex; dual DB for main vs In-House/Service
- Cache: Redis — delete-on-write (invalidateAssetsCache)
- Deploy: Docker Compose prod 8080 / test 9090

### Frontend mental model
index.html is one shell; main.js owns nav → view switching:
- Assets dashboard — dashboard.js (huge)
- Hierarchy — folders/kinds tree (hierarchy.js)
- Inventory — inventory.js
- Projects — projects.js
- Employees, Warranty, DC, OCR, Settings, Admin/RBAC, ARRI, Service portal
- Auth — auth.js; permissions gate nav (view.*)
Versioning around v7.00.

### Backend mental model
server.js is system of record for APIs.

Core domain logic:
1. Asset lifecycle via updateAssetStatus:
   - In Store → available (Mumbai hub)
   - Project → locked to project / on site
   - Under Inspection → returned, hidden until inward check
   - Then release back to In Store
   - Status changes can recurse to children via parentid
2. Sets/components — kits glued by parentid; promotion components→assets
3. Integrity — Postgres trigger against ID in both assets and components;
   Redis cache flushed on writes
4. Auth — JWT + cookies, bcrypt, RBAC
5. Integrations — Zoho, email, Google Sheets, Tally, QR, OCR, PDF/DOCX

### Repo / environments
- Local = GitHub AnuragUb/Asset-Manager (origin), main @ 70bde35
- Also remote official → CineomDevTeam/CineEAM
- Docs say dev→9090, main→8080 but GitHub dev is months behind main

### Quirks
- Docs drift (SQLite vs Postgres; README still mentions PowerShell)
- Giant server.js + dashboard.js
- Dev serves source frontend (useDist = false)
- .env holds secrets; gitignored
- Many one-off check_*/repair scripts from production firefighting

### Bottom line
Production ops tool for cinema/IT asset logistics: hierarchical inventory,
project deployment with inspection on return, QR tracking, admin/audit —
implemented as Postgres + Redis Express app with large vanilla JS frontend,
evolved from older SQLite/PowerShell system.

### Architecture overview
Browser (Vanilla JS SPA)
  → auth / main / dashboard / inventory / projects / ...
  → fetch /api/* + JWT cookies
Express server.js
  → services/ (cache, email, encryption, zoho, tokens, sheets)
  → utils.js → Knex db + dbService + IdGenerator
  → Redis + PostgreSQL
  → currently serves frontend SOURCE (not dist)

### Frontend architecture
- Style: Vanilla ES modules, no React/Vue; ?v= cache busting
- Entry: index.html + main.js
- Gravity well: dashboard.js (~472KB)
- Other large modules: projects.js (~175KB), inventory.js (~97KB), main.js (~70KB)
- Pattern: HierarchyManager, localStorage category, RBAC UI, window.* globals
- Static delivery: forceSource=true / useDist=false

### Backend architecture
- God-file server.js with ~100–160 route registrations
- Thin services/ layer
- utils.js owns Knex dual DB, IDs, Tally, legacy JSON paths

### Database design
- Knex → PostgreSQL; dual connection (main + service for In-House/SERVICE)
- Core tables: assets, components, asset_kinds, folders, projects,
  project_assets, project_orders, delivery_challans, users, companies,
  roles/permissions, auth_tokens, employees, arri_*, zoho_*, inventory_*
- Trigger: no same ID in both assets and components
- Soft deletes (is_deleted); stringly-typed dates/status from SQLite era

### Authentication
- Login → bcrypt (plaintext still accepted and upgraded) → JWT cookie
- Optional remember_token (30 days)
- Middleware: authenticateJWT, authorizeRoles, requirePermission
- Gaps: many unauthenticated routes; open signup; secure:false cookies;
  default JWT_SECRET; default EXTERNAL_API_KEY; debug endpoints open

### Asset lifecycle
In Store → Project → Under Inspection → In Store
Sets recurse; promoteToAsset moves components→assets; parentid sticky

### Inventory module
Parallel stock/catalog; UI always on; migrations gated to asset_manager_test;
FEATURE_INVENTORY_ENABLED can disable backend

### Zoho
zohoService: push assets to Products, pull products/deals, catalog, sync logs;
tokens in zoho_tokens.txt (tracked — risk)

### Service Portal (ARRI)
servicePortal.js + /api/service/* (JWT) and /api/arri/* (often open);
job cards, clients, Google Sheets sync

### Dashboard
Operational cockpit: hierarchy, cards/table, CRUD, DC, bulk import, scanner init

### Scripts
~58 in scripts/ + many root check/fix/repair scripts — ops archaeology

### Migrations
~29 Knex migrations: initial schema → auth → sets → retirement → triggers →
ARRI → Zoho → FK waves → inventory preview family

### Technical debt (high level)
Monolith concentration; docs drift; dual persistence eras; case translation tax;
inconsistent auth; duplicate routes; inventory dual-world; forceSource;
stringly types; script graveyard; window coupling; version query params;
broad Redis KEYS invalidation; weak encryption key handling

### Security issues (high level)
Unauthenticated data APIs; open signup; default secrets; tracked zoho_tokens;
network creds possibly plaintext; debug endpoints; 100mb JSON limit;
auth logging sensitivity; secure:false cookies

### Repository hygiene
Tracked uploads, eng.traineddata, Zoho resource JSON, logos; workstation dump
feel; dual remotes; stale branches; deprecated clients; nested package roots

### Unfinished / partial features
Inventory preview; OCR wiring fragile (import commented); network scanner
inconsistent; assetsReport missing; dist path unused; Electron/PS deprecated;
Tally maturity unclear; signup/multi-tenant incomplete; branch workflow stale;
service vs ARRI API duplication

### Architect verdict
Battle-evolved internal ERP-lite with strong domain ideas, modular frontend
shell around monolithic Express+Postgres core, mid-migration from
SQLite/LAN-trust into JWT/RBAC/Postgres/Redis/Zoho — migration unfinished evenly.

If you became the lead engineer tomorrow, what would be the first ten
engineering improvements, ordered by impact? Do not implement. Explain reasoning.

--------------------------------------------------------------------------------
ANSWER 5
--------------------------------------------------------------------------------
Ordering principle: stop bleeding → lock core domain → make change safe → modernize.

1. Close the open API surface (auth by default)
   Impact: Highest — confidentiality/integrity. Make auth default; allowlist
   only true public routes (login, QR/public asset view).

2. Remove secrets from the repo and rotate them
   Impact: Critical. Tracked tokens, uploads, .env with real credentials,
   default JWT/API keys. Rotate and purge.

3. Stabilize asset lifecycle as a single domain module
   Impact: Highest business correctness. Extract/harden updateAssetStatus,
   promoteToAsset, assign/unassign/inspection, sets, quantity split.

4. Fix auth model consistency
   Impact: Security + admin safety. Signup, plaintext passwords, cookies,
   duplicate RBAC routes, uneven role checks, debug routes.

5. Make Inventory either real or clearly isolated
   Impact: Product/schema clarity. Promote to first-class or quarantine preview.

6. Minimal automated safety net on core flows
   Impact: Delivery speed. Small API/E2E suite around lifecycle + auth.

7. Split server.js into domain routers (no behavior change)
   Impact: Velocity. Mechanical carve after tests exist.

8. Enforce one environment/branch/deploy contract
   Impact: Ops reliability. Single source of truth for branch/port/DB/flags.

9. Repository hygiene pass
   Impact: Onboarding/clone size/leakage. Untrack artifacts; curated tools/.

10. Replace docs drift with short current-state handbook
    Impact: Alignment. Living handbook after facts are stabilized.

Deliberately NOT first: full rewrite, microservices, perfect obfuscation,
big-bang SQLite cleanup, broad clean-code reformatting.
